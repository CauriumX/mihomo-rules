# mihomo 规则体系架构

> 四仓分离。每个仓库单一职责，任一环节故障不影响其余。

## 一、为什么拆

单仓同时承担六件事时，任一环节出问题整个仓库不可用：

| 职责 | 问题 |
|---|---|
| 拉取上游 | 上游失联则构建失败 |
| 聚合规则 | 策略硬编码，改一次跑全量 |
| 审核变更 | 决策无记录 |
| 发布产物 | 9 MB 产物与源码混在一起 |
| 维护模板 | 被规则集更新淹没 |
| 更新订阅服务 | 凭证与数据同仓 |

## 二、四仓架构

```
┌─────────────────────────────────────────────────────────┐
│  mihomo-upstream（私有）                                 │
│    拉取上游、存档快照，不加工                              │
│    产出：Release 资产 snapshots.tar.gz + MANIFEST.json   │
│    失联影响：无（下游用最后快照）                          │
└──────────────────────┬──────────────────────────────────┘
                       │ 下载最新快照
                       ▼
┌─────────────────────────────────────────────────────────┐
│  mihomo-rules（公开）                                    │
│    合并、去重、冲突检测、审核日志                          │
│    产出：ruleset/*.mrs（无上游痕迹）                      │
│    性质：纯函数（给定快照，输出确定）                       │
└──────────────────────┬──────────────────────────────────┘
                       │ 候选产物
                       ▼
┌─────────────────────────────────────────────────────────┐
│  mihomo-apply（公开）                                    │
│    渲染模板 + 版本化发布                                  │
│    产出：v0.1.0/ v0.1.1/ … + latest                      │
│    唯一有发布副作用的仓库                                  │
└──────────────────────┬──────────────────────────────────┘
                       │ jsDelivr CDN
                       ▼
┌─────────────────────────────────────────────────────────┐
│  mihomo-distribute（私有）                               │
│    消费端版本管理 + 健康检查                               │
│    唯一持有订阅服务凭证的仓库                              │
└─────────────────────────────────────────────────────────┘
```

模板源在 `mihomo-template`（公开），发布时由 `mihomo-apply` 渲染。

## 三、故障隔离矩阵

| 故障 | 影响范围 | 恢复方式 |
|---|---|---|
| 上游全挂 | upstream 停止更新 | rules 用最后快照继续构建 |
| upstream 被删 | 无 | 从已有 Release 资产重建 |
| rules 被删 | 无 | 从 upstream 快照重跑（纯函数） |
| apply 被删 | **订阅失效** | 从 rules 产物 + template 源重建 |
| template 被删 | 无 | apply 里有渲染后的模板 |
| distribute 被删 | 无法更新订阅服务 | 手动改模板 URL |
| 订阅服务挂 | 客户端拉不到订阅 | CDN 仍可用，客户端缓存生效 |

**只有 apply 被删会导致订阅失效**，而它是可以从 rules 与 template 重建的。

## 四、关键设计

### 上游地址不公开

`mihomo-rules` 的源码里没有上游 URL —— 通过环境变量注入，未设置则构建失败。

上游快照存在 `mihomo-upstream`（私有），内容原样保存，携带上游的 `# AUTHOR:` / `# REPO:` 头。

产物 `.mrs` 是二进制编码，解码后只有裸域名，无上游痕迹。

### 模板与规则集同版本

模板源写占位符：

```yaml
url: ".../mihomo-apply@{{RULES_VERSION}}/site/AI-Site.mrs"
```

发布时替换为具体 tag。这样模板与规则集不可能错配。

旧架构的缺陷是模板锁 commit 而规则集漂 `@main`，回滚时两者不兼容。`tools/check-version-contract.mjs` 会检出这种情况。

### 凭证隔离

只有 `mihomo-distribute` 持有订阅服务凭证。其余三个仓库只处理公开数据。

即使某个环节被攻破，也拿不到订阅服务的控制权。

## 五、仓库清单

| 仓库 | 可见性 | 变更频率 | 需要凭证 |
|---|---|---|---|
| `mihomo-upstream` | 私有 | 每 6 小时 | 否 |
| `mihomo-rules` | 公开 | 上游变化时 | 否 |
| `mihomo-template` | 公开 | 低频 | 否 |
| `mihomo-apply` | 公开 | 每次发布 | 否 |
| `mihomo-distribute` | 私有 | 消费端变化 | **是** |

## 六、为什么是四仓而不是六仓

最初设计是六池：上游池、聚合池、审核池、应用池、模板仓、分发仓。

工程审计后的结论：

| 原设计 | 处理 | 理由 |
|---|---|---|
| 上游池 | 独立（`mihomo-upstream`） | 上游会失联，需存档 |
| 聚合池 | 并入 `mihomo-rules` | 纯函数，与构建同仓更简单 |
| 审核池 | 并入 `mihomo-rules` | 降级为日志 + 阈值拦截，不值得独立 |
| 应用池 | 独立（`mihomo-apply`） | 发布副作用，tag 必须不可变 |
| 模板仓 | 独立（`mihomo-template`） | 人写 vs 机器生成，变更节奏不同 |
| 分发仓 | 独立（`mihomo-distribute`） | 凭证隔离 |

拆分触发条件（当前均不满足）：

| 拆分 | 触发条件 |
|---|---|
| 聚合独立 | 聚合逻辑 > 1000 行，或需非技术人员改合并策略 |
| 审核独立 | 有第二个人参与审核，或审核频率 > 每天 1 次 |
| 模板并入 apply | 模板文件 < 2 个且无独立贡献者 |

## 七、数据流细节

```
外部上游
    │ snapshot.sh fetch（每 6 小时）
    ▼
mihomo-upstream/work/{a,b,c}/
    │ snapshot.sh pack → snapshots.tar.gz + MANIFEST.json
    ▼
Release: snap-2026-11-12T02-14
    │ gh release download
    ▼
mihomo-rules/upstream/
    │ build-rules.sh check → 变更报告
    │ build-rules.sh apply → ruleset/
    ▼
ruleset/site/*.mrs + ruleset/geoip/*.mrs
    │ 复制到 mihomo-apply
    ▼
mihomo-apply/v0.1.0/
    ├── site/*.mrs
    ├── geoip/*.mrs
    ├── template.yaml（{{RULES_VERSION}} → v0.1.0）
    └── MANIFEST.json
    │ git tag v0.1.0
    ▼
jsDelivr CDN
    │
    ▼
客户端
```
